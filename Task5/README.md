# Task 5. Стратегия миграции и cutover-план

## Выбранный подход

Основа: **Branch by Abstraction** — поверх существующих Excel/1С и файлов вводятся сервисы-фасады (Patient, Appointment, Billing) и API; пользовательские сценарии постепенно переключаются с прямого доступа к легаси на новые контуры. Дополнительно для критичных потоков (**запись пациента**, **платежи**) используется **Parallel Run** — двойной ввод или синхронизированная репликация с ежедневной сверкой до стабилизации.

## Cutover-план (поэтапно)

Обозначения ролей: **Арх** — архитектор; **Dev** — разработка; **Ops** — эксплуатация; **Биз** — владелец процесса / руководитель клиники; **Ан** — аналитик данных.

### Этап 0. Подготовка

| Задачи | Ответственные | Критерии готовности | Метрики / наблюдение |
|--------|---------------|---------------------|----------------------|
| Инвентаризация систем и данных | Арх, Биз, Ops | Реестр источников, владельцы данных согласованы | Документ утверждён |
| Согласование целевой архитектуры MVP | Арх, Биз | C4 и границы контейнеров зафиксированы | Sign-off заказчика |
| Выбор стека: IDP, API GW, СУБД, шина/очередь (при необходимости), платформа DWH | Арх, Dev, Ops | Технические решения записаны (ADR кратко) | Нет блокирующих открытых вопросов |
| Тестовые среды (dev/stage), секреты, базовый мониторинг и логи | Ops, Dev | Stage отражает prod-конфигурацию с масштабом ниже | Дашборд доступности, алерт в тесте |
| Политики шифрования и бэкапов | Ops, Арх | Матрица согласована с ИБ/юристами (по возможности) | Чек-лист включён в релиз |

### Этап 1. Ввод абстракций

| Задачи | Ответственные | Критерии готовности | Метрики |
|--------|---------------|---------------------|---------|
| PatientService как фасад: чтение/запись поверх согласованного снимка Excel/1С или синхронизированной промежуточной БД | Dev, Арх | API покрывает чтение карточки и создание пациента | Доля ошибок API ниже порога на stage |
| AppointmentService над журналами записи | Dev | CRUD записей, конфликты слотов обрабатываются | Тест-кейсы ресепшена пройдены |
| Платёжный шлюз как отдельный контур с журналированием | Dev, Ops | Оплата в тесте, webhook/статусы | Успешность тестовых платежей |
| Интеграционные тесты с 1С (read-only на старте) | Dev | Нет деградации учётной системы | Время ответа интеграции в пределах SLA |

### Этап 2. Миграция данных и функционала

| Задачи | Ответственные | Критерии готовности | Метрики |
|--------|---------------|---------------------|---------|
| Перенос учёта пациентов из Excel в CRM/БД с однократной миграцией и правилами сопоставления | Dev, Ан, Биз | Сверка количества записей и выборочная ручная проверка | % несопоставленных записей → минимум |
| Перенос расписания в новую систему | Dev, Биз | Ресепшен работает в stage как в бою | Обратная связь ресепшена |
| Ограничение прямой правки Excel для перенесённых сущностей (политика + технически read-only копия) | Ops, Биз | Нет новых «обходных» файлов без учёта | Аудит файловых шаров |

### Этап 3. Parallel Run (критичные потоки)

| Задачи | Ответственные | Критерии готовности | Метрики |
|--------|---------------|---------------------|---------|
| Дублирование записи и/или платежей в новое и старое с ежедневной сверкой | Dev, Ан, Биз | Отчёт расхождений ниже порога N дней подряд | Количество расхождений на 1000 операций |
| Устранение выявленных расхождений | Dev | Повторная сверка зелёная | MTTR по дефектам сверки |
| Обучение персонала сценарию «если расхождение — кого звать» | Биз | Инструкция опубликована | Нулевые «тихие» обходы |

Рекомендуемые ориентиры порогов для go-live (уточняются с бизнесом): доля ошибочных записей не выше 0,1–0,5%; критичные расхождения по платежам = 0.

### Этап 4. Переключение и декомиссия

| Задачи | Ответственные | Критерии готовности | Метрики (DORA-ориентиры) |
|--------|---------------|---------------------|---------------------------|
| Переключение фронтов (портал, ресепшен) на новые API как основной канал | Ops, Dev | Cutover-окно завершено, smoke OK | Время простоя в пределах согласованного |
| Ограничение доступа к легаси-Excel и прямым папкам для операционных ролей | Ops, Биз | ACL обновлены | Инциденты доступа |
| Планомерное отключение старых компонентов; исторические данные в архив/DWH по согласованным правилам классификации и загрузки | Ан, Ops | Нет обязательных обращений к старым файлам > X недель | Объём миграции в DWH |
| Ретроспектива и удаление временных адаптеров | Арх, Dev | Список tech debt | Lead time на патчи снижается |

Метрики DORA на период стабилизации: частота релизов (деплой hotfix допускается чаще), lead time изменений, частота инцидентов, MTTR — фиксируются в том же трекере, что мониторинг.

### Управление рисками и откат (rollback)

**Условия отката:** рост ошибок записи или оплаты выше согласованного порога за скользящее окно (например, 1 час / 1 сутки); недоступность нового API ниже SLA; критичное расхождение с 1С, не устранимое в течение согласованного времени.

**Механизм:** feature flags или переключение маршрутизации BFF на режим «чтение из легаси / запись в легаси»; для платежей — приостановка онлайн-канала и возврат к процедуре кассы/ручного ввода в 1С по runbook; откат релиза приложения на предыдущую версию из registry. Данные, созданные только в новой БД за период сбоя, сверяются и при необходимости экспортируются обратно в контролируемый Excel/адаптер — сценарий прописывается в runbook до cutover.
